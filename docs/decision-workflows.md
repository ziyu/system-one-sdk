# Decision workflows with real side effects

**English** | [简体中文](decision-workflows.zh-CN.md)

These repository examples use the public `choiceFrom`, `defineDecision` and `gateChoice` contracts to turn natural-language instructions into application operations. They create sample business data on disk, call a real model, execute the selected handler, and read back the resulting files or ticket records. The documents and tickets are synthetic; model responses and filesystem operations are real. No production customer system, refund service, or email account is contacted.

## Run from the repository

Configure the existing `.env` with `SYSTEM_ONE_API_KEY` for TypeSafe. An endpoint and model are optional. Each command compiles the examples automatically.

```sh
# Read a contract, archive an invoice, then archive the contract.
npm run example:decisions

# Route tickets, preserve a priority, escalate an outage, and close a resolved issue.
npm run example:support

# Supply your own instruction rather than running the built-in demonstration.
npm run example:decisions -- --message 'File the signed Cedar Studio contract in the legal folder.'
npm run example:support -- --message '把所有用户无法登录的工单交给平台值班组，设置为紧急。'

# Use the same workflows through another adapter.
npm run example:support -- --provider openrouter --message 'Route the duplicate-charge ticket to billing.'
```

By default every invocation creates a new directory beneath `.artifacts/decision-examples/` and prints its exact path. Reuse that path to make changes to the same workspace. The following `XXXXXX` is a placeholder for the printed directory suffix.

```sh
# Create only sample data, without credentials or an inference request.
npm run example:decisions -- --init

# Use the printed workspace with a stable request ID.
npm run example:decisions -- \
  --workspace .artifacts/decision-examples/files-XXXXXX \
  --request-id archive-invoice-1 \
  --message '把办公桌椅采购的发票放到财务发票目录。'
```

Repeating the same request ID and instruction returns its stored outcome with `replayed: true`, without another model call or filesystem operation. Reusing that ID for different text returns a conflict. Use a new ID for a new instruction or a retry after a state conflict. The CLI also supports `--message-file <UTF-8 file>` and `--help`; `--message-file` cannot be combined with `--message`.

`--provider typesafe` reads `.env`, `openrouter` reads `.env.openrouter`, and `cloudflare` reads `.env.cloudflare`. Configuration is read directly, so inherited shell keys cannot override the selected file. Cloudflare uses `CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN`; the other files use `SYSTEM_ONE_API_KEY`. These live examples require the selected provider's official origin and do not fall back to another provider. Cloudflare was not live-tested in this workflow verification.

## File inbox

The initial inbox contains an office-supplies invoice, a signed service agreement, and meeting minutes. Generic filenames ensure the model must examine the descriptions rather than rely on a document-type filename convention. You can edit the files or add UTF-8 text files to the generated inbox and give a new instruction.

| Action | Parameters | Application effect |
| --- | --- | --- |
| `file` | Dynamic document and archive folder | Moves the chosen file into `archive/finance`, `archive/legal`, or `archive/meetings`, without overwriting an existing destination |
| `read` | Dynamic document | Returns the actual file contents without moving it |
| `clarify` | None | Records that clarification is required and leaves the inbox unchanged |
| `wait` | None | Leaves documents unchanged |

`listDocuments` reads the actual inbox for every new instruction. Up to 800 characters per document are exposed to the model, together with the available destinations. Candidate values retain their local identity; their paths are supplied by the application, not generated by the model. Empty or ambiguous targets have an explicit `none` option. This small example accepts at most 24 regular UTF-8 files, each at most 32 KiB; it does not parse PDFs or Office documents.

The executor compares a hash of the current file inventory with the one used for inference. A change while the request is pending produces a conflict. Exclusive destination creation prevents an existing archive from being overwritten. The verification runner compares every file path and byte hash before and after the command, including files the operation should not touch.

## Support queue

`workspace.json` contains open tickets, active teams, revisions, and completed-command receipts. The model sees only open tickets and active teams. Resolving a ticket removes it from the candidate set for the next instruction. Each instruction reads the latest persisted state, so a follow-up correction can reassign the same ticket using its current priority.

| Action | Parameters | Application effect |
| --- | --- | --- |
| `assign` | Dynamic ticket, dynamic team, `keep / normal / high / urgent` priority operation | Updates the selected ticket and increments its revision |
| `resolve` | Dynamic open ticket | Sets its status to `resolved` and increments its revision |
| `clarify` | None | Records the need for clarification without changing a ticket |
| `wait` | None | Leaves tickets unchanged |

`keep` is an explicit operation: it leaves the existing priority untouched. It is selected when priority is omitted or the user explicitly asks to preserve it. The application does not replace an omitted priority with `normal`, and does not infer a priority change merely from the issue's severity. Ticket changes and their receipt are written together by atomic JSON replacement.

## Reuse the implementation

| File | Responsibility |
| --- | --- |
| `examples/scenarios/files.ts` | `fileDecision`, real inventory loading, and `runFileCommand` |
| `examples/scenarios/support.ts` | `supportDecision`, persisted queue, and `runSupportCommand` |
| `examples/scenarios/workspace.ts` | Explicit policy, locking, receipts and atomic JSON replacement |
| `examples/scenarios/client.ts` | Provider configuration and instrumented native Fetch |
| `examples/scenarios/cli.ts` | Free-form instructions, workspace selection and readable results |
| `examples/scenarios/cases.ts` | Expected outcomes used only by the verification runner |

`runFileCommand(client, directory, message, requestId, options?)` and `runSupportCommand(...)` accept any `EvaluationClient`. They return the complete normalized evaluation, selected branch and parameter IDs, each policy outcome, and the execution result. Replayed calls return their receipt without fabricated inference metadata. The CLI saves a `run-*.json` report, including partial results when a later command fails.

The SDK itself remains responsible for evaluation and typed resolution. The filesystem, ticket revisions and handlers belong to these Node.js examples. In a consuming application, import the SDK from `@system-one-ai/sdk`, `@system-one-ai/sdk/decisions` and `@system-one-ai/sdk/policies`, and implement persistence using that application's storage layer.

Every action and each relevant selected-branch choice must pass `minProbability: 0.8` and `minMargin: 0.2`. `clarify` and `none` are explicit abstentions. Unselected branches do not block execution. API failures stay errors; weak evidence stays uncertain. These thresholds are example configuration, not a recommended universal cutoff.

The examples are serial local workflows with an exclusive writer lock. They reject a busy workspace promptly. File movement and receipt storage are separate filesystem operations, so they do not promise crash-atomic or distributed exactly-once execution. Use transactions and an operation journal appropriate to your production system when extending the handlers.

## Verify model decisions and actual effects

```sh
# Offline executor tests, including stale state, collision, cancellation and replay.
npm run test:scenarios

# Twenty real inference requests per provider, no retries.
npm run test:live:decisions -- --provider typesafe
npm run test:live:decisions -- --provider openrouter

# The fixed dataset can also be run by partition.
npm run test:live:decisions -- --provider typesafe --phase development
npm run test:live:decisions -- --provider typesafe --phase holdout
```

The dataset contains 14 primary cases and 6 additional formulations, including English and Chinese commands, semantic target selection, ambiguous instructions, unsupported operations, an empty inbox, priority preservation and successive ticket corrections. `holdout` names the extra-formulation partition; after it has been used during development it is not an independent statistical holdout.

Expected answers never enter `state` or question descriptions. Clear commands must select the expected action and arguments **and complete the expected disk changes**. Returning uncertainty is a failure for those cases. Ambiguous and unsupported commands must preserve business data. Every passing case is then replayed, checking that no additional inference or mutation occurs. Failed checks exit nonzero and remain in their original reports.

Reports are saved in fresh `.artifacts/live-decisions-<provider>-*/report.json` files and contain source hashes, inputs, expected outcomes, full model answers, gates, before/after state, timing, token coverage, request traces and errors. Latency includes the SDK and network, not just model compute. Credentials and authentication headers are excluded.

On September 18, 2026, the final 20-case suite passed **20/20 through TypeSafe** and **20/20 through OpenRouter**, with 20 replay checks each. The original OpenRouter run passed 19/20: a separate boolean question about whether priority was specified made “keep its existing priority” uncertain. Replacing that extra question with the explicit `keep` choice fixed the observed case without lowering thresholds. Initial and final results are preserved in [the validation record](validation.md).

This is an integration sample, not a production accuracy benchmark. The design follows TypeSafe's [closed-set function calling pattern](https://docs.typesafe.ai/cookbooks/function_calling); probability thresholds and uncertainty handling are discussed in its [confidence documentation](https://docs.typesafe.ai/confidence).
